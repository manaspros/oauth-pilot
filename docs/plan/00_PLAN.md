# 00 — Plan: OAuth Pilot

> Read this first. Then `01_ARCHITECTURE.md`, then the spec your task points at.

## One-line pitch

Tell a developer, **for the actions their agent needs**, how hard it is to get a provider OAuth app production-ready. Show the critical path and what to start first. Then do as much of the setup as possible for them, from a web page, from Claude via MCP, or from a Claude Code plugin.

## The problem we solve (short)

Full framing: `docs/research/01_problem_framing.md`.

- A Composio **auth config** points at a **provider OAuth app**: either Composio's managed app or the developer's own. Each end user's **connected account** is a token minted through that config.
- 124 toolkits have a managed app and 258 do not. Even with a managed app, production usually means your own app, for branding, dedicated quota and custom scopes.
- Switching apps later forces every user to re-authenticate. Choosing the wrong path early is expensive.
- **Difficulty is set by scopes, not by the app.** Gmail read is a restricted scope and needs a yearly security assessment. Calendar read is a sensitive scope and needs brand verification. Same vendor, different weeks.
- The slow part is **waiting for review**, and developers find out late.
- Most prerequisites aren't code: a domain, a privacy policy, a demo video, an admin, a legal entity.

## What we build (two deliverables + one shared core)

| # | Deliverable | Who uses it | Mode |
|---|---|---|---|
| A | **Autonomous agent system**: a LangGraph JS graph run by a web app (HTTP + SSE) and, independently, by an MCP server that runs the graph in-process | Developers on the web page; Claude (any MCP client) delegating "go research X and report back" | Autonomous: runs end to end and reports back |
| B | **Claude Code plugin `oauth-pilot`**: skills plus subagents, wired to A's MCP server, with an in-session fallback | Developers inside Claude Code | Interactive: Claude does the steps with the developer, drives the browser and hands off at login, 2FA or payment |
| — | **Shared core**: guide schema, difficulty rubric, critical-path math, markdown renderer | Both | — |

Both deliverables produce the **same Guide JSON** (`02_GUIDE_SCHEMA.md`). The web page renders it as a React Flow diagram and the plugin renders it as markdown.

## Product decisions (locked; change only via DECISIONS.md)

1. **Scope-aware verdict.** Input is the app plus an optional use case or list of Composio tools. If tools are given, map tools to scopes with Composio's "get required scopes" endpoint, then map scopes to approval tier.
2. **Two clocks, not one.** Every guide shows *time to first working connection* (you, testing) and *time to production* (any user, including review wait). This is what developers actually ask.
3. **A five-tier difficulty rubric** (0 Instant → 4 Gated), defined in `02_GUIDE_SCHEMA.md §Tier rubric`. The tier is computed from facts, not chosen by the LLM's mood.
4. **Every step has an actor:** `agent` / `developer` / `admin` (someone else: Workspace admin, legal) / `provider` (waiting on review). This answers "what can an agent do for me and where do I take over".
5. **An evidence ledger:** every factual claim is `tested` (we actually did it), `sourced` (URL, quote and date) or `inferred`. Nothing is marked `tested` unless a command or browser action really ran.
6. **Draft, then verify with fresh context** (the Elephant–Goldfish pattern, kept to one line in the README). A drafting call with full research context writes the guide. A separate verifier call with fresh context sees only the claims and their cited sources, then downgrades or removes what the sources don't support. This mirrors google/elephant-goldfish-model, which we also use to review this plan.
7. **"Start today" + risk playbook:** each verdict names the slowest step to start now. Each guide lists risks with the error text you'll see → fix, for example `Error 403: access_denied — app not verified` → add test users or submit for verification.
8. **The library is generated by the agent and then audited** against hand-built evidence packs (`research/apps/*.md`). The audit is our verification report: what was right, what we corrected, what we couldn't verify.
9. **Shareable:** every guide has a stable URL `/guides/<slug>` and a "copy as markdown" button.

## Demo app set (varied on purpose)

| App | Composio | Why it's in the set |
|---|---|---|
| Linear | managed | Easy baseline: self-serve OAuth app, no review |
| Google Calendar | managed | Sensitive scopes, brand verification, testing-mode traps |
| Gmail | managed | Restricted scopes, CASA security assessment, the long pole |
| Salesforce | managed | Org-level admin setup (connected app or External Client App), admin is a separate actor |
| Shopify | bring-your-own | No managed app; public vs custom app, app review |

Slack is the **live-generation demo** app: not in the library, so reviewers watch the agent build it.
All facts above are hypotheses until the evidence packs (T05–T07) confirm them.

## Out of scope

- All 100 guides. We ship 5, plus live generation for any app.
- Completing real provider approvals or paid accounts.
- Multi-user accounts or auth on our own site. Guides are public URLs.
- Automatic re-verification cron. This is a documented "next step" in the README.

## Success criteria (what the reviewer will try)

1. Open the site, see 5 guides with tier badges and both clocks.
2. Open Gmail: the diagram shows the CASA wait on the critical path, the evidence ledger shows sources, and uncertain items are marked as such.
3. Type an unfamiliar app (for example "Pipedrive" or "Calendly") and watch the agent graph light up node by node. A guide appears in under ~3 minutes.
4. In Claude Code: `/oauth-pilot:oauth-guide notion` returns a verdict. `/oauth-pilot:oauth-setup linear` walks through creating the Linear OAuth app, writes `.env` and creates the Composio auth config.
5. In any MCP client: `oauth_guide_start` → `oauth_guide_status` reports back a summary.
6. README: setup, decisions, limitations, verification report link.
